# 定期更新の診断とログ

コンテナ内で次を実行する。Claude への質問や API 呼び出しは不要。

```bash
/usr/local/bin/firewall-refresh.py --status
tail -n 80 /tmp/claude-firewall-refresh/refresh.log
tail -n 80 /tmp/claude-firewall-refresh/refresh.log.1
```

`--status` は保存済みの状態を JSON で表示し、更新処理を実行しない。
時刻は UTC。終了コード 0 は「状態を読めた」の意味で、更新成功を保証しない。
状態がない・壊れている・読めない場合は終了コード 1 と理由を表示する。
ファイアウォール無効時には監視も起動しないので、状態がないのは想定内。
有効時に状態がない場合は正常とみなさず、監視の未起動・終了、または診断の保存失敗を疑う。
`pgrep -af firewall-refresh.py` でプロセスの有無を確認する。起動時のロック取得失敗などは
対話 UI に表示されないため、状態がないことだけでは原因を特定できない。

## 見る項目

| 項目 | 意味 |
|---|---|
| `phase` | `waiting` は次の試行待ち、`running` は更新処理中 |
| `result` | 直近の完了結果。まだ試行が完了していなければ `not_run` |
| `last_attempt_at` | 最後に試行を始めた時刻 |
| `last_completed_at` | 最後に試行が終わった時刻 |
| `last_success_at` | エラーなしで完了した最後の時刻。未成功なら null |
| `consecutive_failures` | `partial` / `failure` の連続回数。成功すると 0 に戻る |
| `last_failure` | 最後の失敗時刻・分類・終了コード・出力末尾の概要。回復後も保持する |
| `diagnostic_errors` | 現在のログ・状態保存エラー。各保存が成功すると対応する項目を消す |
| `last_diagnostic_error` | 最後の診断保存エラーの時刻・操作・概要。復旧後も保持する |
| `heartbeat_age_seconds` / `stale` | 状態記録からの経過秒数と鮮度。60秒超、または時計の逆行で未来時刻なら `stale: true` |
| `running_for_seconds` | 更新中の経過秒数。待機中は null |
| `started_at` / `pid` | この監視プロセスの開始時刻と PID |

結果は次のように分ける。

- `success`（0）: ドメイン更新と期限切れ削除が、エラーを報告せず完了した。
  NXDOMAIN や許可範囲外アドレスの除外は、従来どおり警告扱いで失敗数に含めない。
- `partial`（75）: サイクルを最後まで試したが、ドメイン更新または期限切れ削除で
  エラーがあった。「一部の IP 更新が必ず成功した」という意味ではない。
  全ドメインの DNS 解決が失敗しても、サイクルを完走した場合はこの分類になる。
- `failure`（それ以外の非0）: コマンドの起動失敗、設定不正などで更新が完走しなかった。

`partial` / `failure` でも監視ループは続き、次の試行へ進む。
成功していた時刻は失敗で上書きしない。`running` の間の `result` は前回の結果なので、
現在の試行が成功しているとは解釈しない。

## 更新が止まったように見えるとき

監視は各試行の前後と、更新処理中は約5秒ごとに状態を更新する。
`stale: true` なら監視停止、状態書き込みの失敗、CPU 停滞などを疑う。
PID の再利用もあるため、状態だけで停止原因を断定しない。
状態が新しくても `running_for_seconds` が増え続ける場合は、更新コマンドが長時間実行中。
ドメイン数が多ければ処理も長くなるため、ログ末尾と併せて調べる。
更新コマンド全体のタイムアウトは、この機能では追加しない。

容量不足や保存先の削除でログ・状態を保存できなくても、更新処理と次の試行は継続する。
保存先は再作成を試み、書き込めるようになれば診断を再開する。保存できない間のログは失われる。
状態保存自体が失敗している間は、新しいエラー情報もファイルへ反映できないので、
既存状態の鮮度とプロセスの有無を確認する。診断保存の失敗は更新処理の終了コードとは分けて記録する。

監視を起動し直すと、状態は新しいプロセスの `not_run` から始まる。以前の成功・失敗は
そのプロセスの実績として引き継がない。ログの直近2世代は残る。

## ログの保持と権限

- 現行 `refresh.log` と前世代 `refresh.log.1` はそれぞれ **256 KiB**、合計 **512 KiB** 以下。
  満杯になった時点で世代を入れ替え、それより古い内容は捨てる。
  大きな1行や、終わらない大量出力も小さな単位で読み、上限を超えてから一括切り詰める方式にはしない。
  世代の先頭は行や UTF-8 文字の途中になる場合がある。
- `state.json` はログとは別に保存し、一時ファイルからの置換で途中の JSON を読ませない。
  失敗概要は出力末尾の最大1024文字。原因がそれ以前にある場合は2世代のログを確認する。
- `/tmp/claude-firewall-refresh/` は実行ユーザー所有・モード700。記録はコンテナ内の非特権
  ユーザーが行い、sudo の許可対象は従来の `init-firewall.sh` のまま。
  これらは同じユーザーが書き換えられる運用診断であり、改ざん耐性のある監査記録ではない。
- `/tmp/claude-firewall-refresh.lock` のファイルロックで監視の二重起動を拒否する。
  診断ディレクトリの再作成でもロックを保持するため、このファイルは外に置く。監視中は削除しない。
  手動の `init-firewall.sh` 実行を禁止するロックではない。
- 更新終了後の待機は従来どおり15秒。対話 UI へ定期ログは出さない。
  以前の `/tmp/claude-firewall-refresh.log` への無制限追記は行わない。

`init-firewall.sh --refresh-domains` の終了コード75は、監視が部分失敗を見分けるために追加した。
ドメインごとの更新継続、期限切れ削除の試行、次のサイクルでの再試行方針は維持する。
この変更を既存プロジェクトで使うには、`c3c claude -b <プロジェクト>` で再ビルドする。
