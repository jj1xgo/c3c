# Sandbox の今後の検討候補

記録日: 2026-09-13。確認対象: `main` の `efb89c1`。

このメモは、信頼できるリポジトリだけを扱う運用を前提にした検討候補である。実装の決定・着手予定ではなく、ここに挙げた候補を新たに Issue 化するものでもない。評価はコードと既存の報告に基づき、この検討で実コンテナの侵入・迂回テストは行っていない。

## 前提と評価

対象リポジトリと `.claude-container.d/` の設定は、運用者が管理・確認する。主な目的は、普段の開発でエージェントの誤操作が及ぶ範囲を限定することとする。

この前提では、現在の非 root 実行、ネットワーク管理権限の剥奪、エグレス制限、ホストの実行設定の読み取り専用保護は、用途に合った対策と評価できる。ただし、信頼できるリポジトリであっても、依存パッケージや外部から読む文章まで同じように信頼できるとは限らず、エージェントの誤操作も残る。

リポジトリ側から追加マウントや通信制限を指定できることは、この運用ではプロジェクトごとの設定を管理するための機能として扱う。設定をホスト側へ移すことは、現時点の最優先事項とはしない。

## 検討候補

| 候補 | 目的・検討内容 | 再検討するきっかけ |
|---|---|---|
| 共有マウントの範囲と書き込み権限 | `/data`・`/shared` を必要な範囲に絞る。参照だけの用途には読み取り専用を選べる仕組みを検討する。共有ノートへの書き込みなど既存の用途は維持する。 | 参照専用の利用が増えたとき、複数プロジェクト間の変更波及が問題になったとき。 |
| 持ち込むトークンの最小化 | 必要なトークンだけを渡し、対象リポジトリと操作権限を絞る運用を確認する。非 export や読み取り専用マウントは、コンテナ内コードによるトークンの読み取り・利用を禁止する仕組みではない。 | 新しい外部サービスや書き込み権限を追加するとき、複数プロジェクトで同じトークンを使うとき。 |
| CPU・メモリ・プロセス数の上限 | 暴走や大量の子プロセス生成によるホストへの影響を抑える。ビルド・テストに必要な資源を測り、Podman・ホスト側の既存制限も確認して設定方法を検討する。 | 並列セッションが増えたとき、ホストの応答低下やメモリ不足が起きたとき。 |
| 認証・状態ディレクトリのプロジェクト別分離 | 共有する状態と個別に持つ状態を整理し、セッション間の変更波及を減らす。認証更新や既存の履歴共有との両立を確認する。 | プロジェクト間の信頼度が異なる場合や、共有状態の衝突・汚染が問題になったとき。 |
| 実コンテナでの隔離の継続確認 | マウントの保護、権限剥奪、通信制限が実際に効くことを検証する。これは既存の [#105](https://github.com/jj1xgo/claude-container/issues/105) で扱い、重複 Issue は作らない。PR の必須チェックを増やさず、手動・定期実行とする。 | Dockerfile・起動処理・通信制限や、Podman 等の実行環境を変更するとき。 |

## 前提が変わった場合

信頼できないリポジトリや未確認の外部 PR を扱う運用に広げる場合は、この評価をそのまま適用しない。対象リポジトリから変更できないホスト側でマウント・通信制限を管理すること、認証情報を共有しない構成、さらに強い実行環境の分離を改めて検討する。
