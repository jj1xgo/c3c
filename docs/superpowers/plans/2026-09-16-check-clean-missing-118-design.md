# 削除済みプロジェクトのイメージ清掃設計（#118）

状態: 設計・実装レビューの指摘を反映し、実装とローカル検証を完了。コミット・PR 作成前。

対象: [#118](https://github.com/jj1xgo/claude-container/issues/118)。調査基準は `b3917de`。

## 目的と範囲

通常の `--check` に残存イメージの診断を追加する。明示した `--check --clean-missing` だけが、元のプロジェクトパスの欠落を確認できるイメージを削除する。既存の `clean_project()` / `clean_all()` は全体への prune と失敗を隠す分岐を持つため、新経路から呼ばない。

新経路はイメージだけを対象とする。台帳、ネットワーク、コンテナ、MCP 承認記録、`.build-context/` は変更しない。台帳を残すことで、削除済みパスを後から既存の `--clean <path>` で指定できる状態も保持する。この旧コマンドは全体の dangling prune を伴うため、新コマンドの失敗時に自動で実行しない。

## CLI と対象の選び方

- `--check`: 台帳の各プロジェクトを従来どおり診断し、ローカルイメージも調査する。台帳が空でもイメージ調査を省略しない。
- `--check <path>...`: 指定パスだけを診断する。イメージ報告も、ラベルまたは台帳との対応がそのパスに確定したものに限定する。
- `--check --clean-missing [<path>...]`: 同じ対象選択で清掃する。引数なしでは台帳のパスと、有効なラベルから復元できるパスを対象とする。台帳にないという理由だけでは削除しない。
- `--clean-missing` 単独、`--clean` と `--check` または `--clean-missing` の併用は引数エラー（終了コード 2）。全清掃の dispatch より先に検査する。従来の危険な `--check --clean` も明示的なエラーへ変更する。
- `--check` と `-b` の併用は従来どおり `-b` を無視する。

欠落パスの識別では既存の論理絶対パスとキー算出規則を維持する。symlink の実体パスへ置換しない。相対パスは論理 cwd を基点に正規化する。空文字、改行、先頭 `//`、復元不能な cwd は清掃対象にしない。未知のパスや malformed なラベルから名前の一致を推測しない。

## イメージの由来

新しいビルドには次のラベルを Dockerfile の最後（`ENTRYPOINT` と `CMD` より後の単一 `LABEL` 命令）で記録する。Compose の build 引数は launcher が通常 run の暗黙ビルドと明示 build の両方に渡す。利用側 env を根拠にせず、確定した `WORKING_DIR` と `PROJECT_NAME` から導出する。`CC_PROJECT_METADATA`、`CC_PROJECT_PATH`、`CC_PROJECT_NAME` は全て既定値を空とし、launcher が有効なパスの場合だけ三つを一緒に設定する。直接 Dockerfile をビルドしたテストイメージの空ラベル三つは由来情報なしとして扱う。

| ラベル | 値 |
| --- | --- |
| `claude-container.project-metadata` | launcher 経由では `1`、その他は空 |
| `claude-container.project-path` | 起動時の論理絶対パス |
| `claude-container.project-name` | 既存の basename とパスハッシュによるキー |

ラベルはホストのパスを含む。README に、イメージの共有・export 時にもこのメタデータが含まれることを記載する。既存イメージに後付けしない。新ラベルは次回ビルドで付く。

`podman images --all --format json` と対象の `podman image inspect` を使う。元パスの検査先と一致させるため、全呼び出しに `--remote=false` を付けてローカル Podman に限定する。読み取り検査は30秒を上限とし、ストレージを更新する削除処理は強制終了せず完了を待つ。タグ数に応じた同一 ID の完全一致行はまとめ、内容が矛盾する重複は検査不能とする。JSON の検査に失敗した場合は空一覧へ置換しない。`Names` / `RepoTags` の現在の名前と、`History` の過去の名前を混同しない。名前・label・ID の型を検証する。

削除可能なのは以下のすべてを満たすものに限る。

1. ラベルの schema、パス、再計算したキーが一致する。または上記三つの由来ラベルが全て無いか全て空の旧イメージで、台帳の完全一致パスから現在の名前を一意に復元できる。既存の `asset-hash` / `base-image` / `ipv6-support` ラベルの有無はこの判定に影響しない。
2. 現在の名前が `localhost/<key>_claude-auth-workspace:latest` だけである。別タグや別名を持つ共有イメージは保護する。
3. パスが下記の欠落判定を満たす。
4. コンテナ参照がなく、再検査にも成功する。

不完全・矛盾した由来ラベルがある場合は旧イメージ用の台帳フォールバックを使わない。キーの衝突や複数パスに対応する場合も削除しない。キーは ASCII のみ小文字化し、既存 Bash と同じサニタイズ後に40文字へ切り詰める。ハッシュ対象は `os.fsencode(path)` のバイト列とし、Unicode の `str.lower()` を使わない。

名前がないイメージはラベルがあっても候補報告だけとする。派生イメージはラベルを継承でき、名前を失うと対象を断定できないため。名前なしの個別 ID 表示は有効な由来ラベルで欠落パスを確認できたものに限定し、生存パスの旧ビルドや由来不明の中間イメージは件数だけを表示する。詳細確認には `podman images --all --no-trunc` と `podman image inspect <id>` を案内する。古いラベルや名前履歴から由来を推定できても削除しない。名前付きで元パスが生存している台帳外イメージは個別に報告し、削除しない。手動確認が必要な ID と、保留した理由を表示する。

## 欠落・参照・削除の判定

Python 標準ライブラリでパスを検査する。`exists()` の false や Bash の `! -e` を削除根拠にしない。パス成分を順に `lstat` / `stat` し、到達可能なディレクトリの下で成分が `ENOENT` となったときだけ欠落とする。`EACCES`、`ENOTDIR`、`ELOOP`、I/O エラーは検査不能。途中・末尾の壊れた symlink は検査不能とし、元 symlink 自体が除去された場合と区別する。通常ファイルへの置換も清掃不可。

通常のヘルパー診断が呼ぶのは `podman images --all --format json` だけで、コンテナ未使用までを保証しない。清掃候補がある場合だけ `podman ps --all --external --no-trunc --format json` で稼働中、停止中、Buildah 等の外部ストレージコンテナの `ImageID` を確認する。未知の形式・取得失敗があれば削除を始めない。参照があれば理由を表示して保留する。既存 launcher の通常診断によるラベル検査は従来どおり継続する。

対象ごとに削除直前に image inspect、パス判定、コンテナ参照一覧を再確認する。削除はフル ID に対する `podman rmi --no-prune <id>` のみ。`--force`、`--all`、`--ignore`、prune、コンテナ削除を使わない。事前検査後の参照追加は Podman の非強制削除の拒否も防御とする。すべての状態を原子的にロックする機能ではないので、同時にビルド・タグ変更・起動・移動を行わない運用を README に記載する。

削除後は `podman image exists <id>` の終了コード 1 を消失確認として扱い、0 やその他のコードは失敗。標準エラーを報告し、例外を成功へ変換しない。

`--no-prune` により中間イメージ・キャッシュは残る。既存の旧ビルドも残りうるため、名前付きイメージの削除とディスク使用量の回収を同一視しない。共有レイヤーや中間イメージ次第では回収量が小さいことを README と清掃結果に記載する。名前なしイメージの保留だけでは、選択した名前付きイメージの清掃を失敗にしない。

未マウントの媒体や切断中の共有にあるプロジェクトも `ENOENT` になりうる。削除する前に全対象の元パスと ID を表示し、媒体を接続した状態で実行するよう README に記載する。

## 台帳と結果

台帳は全ケースで保持し、一時台帳も作らない。読み取り不能、symlink、通常ファイル以外の場合はその情報を削除根拠に使わず FAIL とする。台帳だけにある欠落パスで対応する名前付きイメージが無い場合は「対象イメージなし、台帳は保持」と報告して終了コードを上げない。これによりイメージ削除後の再実行は同じ結果へ収束する。明示パスが台帳にもラベルにも対応しない場合は対象未確認として FAIL にする。

出力は診断、清掃対象、削除成功、対象なし、保留理由、失敗を区別し、台帳とキャッシュを保持したことも表示する。終了コードは「既存の実在プロジェクト診断の FAIL」または「ヘルパーの失敗」の論理和で 1 とする。清掃モードでは全指定パスの到達性をヘルパーが先に判定・報告する。Bash の既存検査ループは開けるディレクトリだけを診断し、開けないパスの重複 FAIL を出さない。到達性の変化も成功に隠さないよう、ヘルパーの判定結果（directory / missing / unverifiable）を一時 JSON で渡し、directory と判定されたパスは既存検査に必ず渡す。

参照中・別名付きの対象イメージ、由来矛盾、パス検査不能、Podman 失敗はヘルパーの FAIL。名前なし・元パス不明の候補報告だけなら WARN として終了コードを上げない。通常モードでは欠落台帳パスは従来どおり FAIL。清掃モードで成功した後も通常 `--check` では欠落台帳パスが報告されることを README に明記する。

通常 `--check` は対象リポジトリ、台帳、`.build-context/`、イメージを変更しない。podman / Python がない通常診断では残存イメージ調査を明示的にスキップし、既存診断を継続する。清掃要求時に必要な依存がない場合は FAIL とする。

## 実装の境界と関連 issue

ホスト用 `project-images.py` に inventory、由来判定、欠落判定、限定した清掃を集める。コンテナへ COPY しない。launcher は引数検査・build 引数・既存診断との集約を担当する。ヘルパーは `python3 -I` で固定パスから起動し、shell を実行せず、Podman に配列で引数を渡す。設定ファイルを実行・読み込みしない。相対パスは launcher が検証済みの論理 cwd で絶対化し、`--project=<absolute-path>` の形で渡す。ヘルパー不在は配布物の不整合として清掃では FAIL、通常診断では明示的な SKIP。

`#110` の欠落診断文は今回の判定と矛盾しないよう、「開けない」と「確認された欠落」を区別する。削除済み cwd で `PWD` がない既存 `--clean` の改修は本件に混ぜない。

## 検証

ダミー Podman の状態機械と実 launcher のテストを `--launcher-only` に組み込む。台帳の新パス更新、旧 symlink パス、権限拒否、通常ファイル、壊れた symlink、停止・実行・外部コンテナ、失敗コード、JSON 破損、複数タグ、衝突、無関係なイメージを含む。通常 `--check` は変更前後のファイル snapshot と Podman の呼び出し列で無変更を確認する。清掃モードでも成功・部分失敗・再実行・対象なしの全ケースで台帳の内容とモードが不変であることを検証する。

実 Podman はテスト専用の storage root / runroot で小さいローカルイメージを作り、実ユーザーのストレージを清掃しない。停止・実行・Buildah の参照保護、`--no-prune` による親保持、最終ラベル、実 JSON 形式を確認する。Buildah が使えない場合はその項目を `not run` とし、未検証を成功としない。
