# 削除済み cwd からの `.`・`..` 指定を幽霊名で進めず止める計画（#122）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

> 実行担当: Codex（host の checkout で `/goal` に渡す。末尾「実装者」参照）。編集対象は `claude-container`・`test-build.sh`・`README.md` の 3 ファイルで、置換文と Expected は逐語で確定しており（計画時にコンテナ内の使い捨て worktree で赤→緑を実測済み）、実装中に設計判断は残らない。

**目的:** cwd が削除済みの状態で `claude-container --clean .`（または `..`）・通常起動 `claude-container .`・`--check .` を打つと、bash の `cd .` が成功して `pwd -L` が文字どおり `.` を返し、`.` の sha256 由来の幽霊名 `project-cdb4ee2a`（`..` なら `project-5ec1f7e7`）でイメージ・ネットワーク・ビルドコンテキスト・MCP 承認記録の清掃、起動台帳への `.` の記録、`--check` の診断が走る欠陥（fail-open）を直す。台帳に `.` が記録された後は、通常の `--check` が「起動台帳に正規化された絶対パス以外の行があります」で失敗する二次被害もある。

**構成:** `resolve_project_directory()` の通常経路で `pwd -L` の結果が `/` で始まらなければ `guard_fail` で止める（`run_check_mode()` の相対パス扱いや #110 の分岐と同じ「候補を作らず止める」方針）。`check_one_project()` も同じ条件で `[FAIL]` にして幽霊名の診断をしない。`run_check_mode()` がイメージ診断ヘルパーへ渡す正規化（`printf '%s.' "$PWD"`）は変えない — 同じ状況では `.` が渡り、`project-images.py` が既存の検証「対象は改行・先頭 // を含まない正規化済み絶対パスで指定してください」で拒否するため（fail-closed のまま。実測済み）。

**根拠（1 次情報、2026-09-18 にコンテナ内で実測。bash 5.2.37）:**

- bash は起動時に環境の `PWD` を `getcwd()` と照合し、cwd が削除済みで照合できなければ `PWD` を捨てる。その状態の `cd -- . && pwd -L` は rc=0 で `.` を、`cd -- .. && pwd -L` は `..` を返す。環境に `PWD` が無い場合も、削除済みディレクトリを指す stale な `PWD` を渡した場合も同じ（launcher は常に新しい bash プロセスなので、この 2 通りが利用者の実際のシェル状態）。`[[ -d . ]]` と `pwd -P` は削除済み cwd でも成功するため検知に使えない。使えるのは「`pwd -L` の結果が `/` で始まるか」だけ。
- 再現（main `96e40b9`、ダミー podman、`env -i HOME=<仮> PATH=<ダミー>:$PATH`、cwd を `rmdir` してから起動）:
  - `--clean .` → `PROJECT: project-cdb4ee2a`、`rmi localhost/project-cdb4ee2a_claude-auth-workspace`・`network rm project-cdb4ee2a_default`・`rm -rf .build-context/project-cdb4ee2a`・`image prune -f` が走り rc=0。
  - `.`（通常起動） → `PROJECT: project-cdb4ee2a`、起動台帳に `.` が 1 行記録され、`compose ... -p project-cdb4ee2a ... run` まで進み rc=0。
  - `--check .` → 直前の通常起動で台帳に `.` が入っていたため `[FAIL] イメージ診断・清掃に失敗しました: 起動台帳に正規化された絶対パス以外の行があります`、続いて `[OK]   プロジェクトディレクトリ実在: .` と `PROJECT_NAME: project-cdb4ee2a` で診断が進む。
  - `--clean ..` → `PROJECT: project-5ec1f7e7` で同様に清掃、rc=0。
- 計画の dry run（使い捨て worktree に Task 1〜3 を逐語で適用）: Task 1 後の `--launcher-only` は新規 8 件が `[FAIL]` で `PASS=238 FAIL=8`。Task 2・3 後は `PASS=246 FAIL=0`、`lint.sh` rc=0（コンテナ内のため compose 検証はスキップ、shellcheck 0.10.0 の版差 WARNING は #123 で既知）、`git diff --check` 出力なし。修正後の各ケースの出力は Task 2 の Expected に記載。
