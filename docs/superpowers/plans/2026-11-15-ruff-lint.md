# lint.sh に Python の静的な検査（ruff の F 系）を足す 実装計画（#264）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目的:** `lint.sh` が、ルートと `tests/` の Python に ruff の F 系（使っていない import・変数、未定義の名前など）の検査をかける。CI では版と SHA256 を固定した ruff で必ず検査し、手元に ruff が無い環境（作り直す前のコンテナなど）では WARNING を出してこの検査だけ飛ばす。今ある 7 件を直す。

**構成:** 検査は `lint.sh` の関数 `run_ruff_check` にまとめ、Python の構文の確認の直後に呼ぶ。関数は bash の組み込みと `ruff` だけを使い、試験 `tests/test-lint-ruff.sh` が関数を `sed` で抜き出して偽の `ruff` で確かめる（`tests/test-lint-compose-checks.sh` と同じ形）。CI は shellcheck と同じく GitHub Releases から版と SHA256 を固定して取り、`LINT_REQUIRE_RUFF=1` で `lint.sh` を回す。

**使う技術:** bash、ruff 0.16.4（CI の固定版）、GitHub Actions、shellcheck（`./lint.sh`）。

**仕様（持ち主が承認した短い設計、2026-11-15）:**
- 検査: `ruff check --isolated --no-cache --select F --output-format concise -- <ファイル>`。対象は構文の確認と同じ、ルートの `*.py` と `tests/*.py`（構文の確認の `Path.glob` と同じく `.` で始まる名前も含める。`--isolated` は手元の ruff の設定に結果を左右させないため、`--no-cache` は作業ツリーに `.ruff_cache` を作らないため）。
- ruff が無いとき: WARNING を出して飛ばす（持ち主決定）。`LINT_REQUIRE_RUFF=1` のときだけ ERROR で失敗にする（CI が渡す。`LINT_SKIP_COMPOSE` と同じ、環境変数で切り替える形）。
- 版: CI はホストの開発環境と同じ 0.16.4 に固定する（持ち主決定。shellcheck と同じ考え方）。`lint.sh` は ruff の版を表示し、CI の固定版と違えば WARNING を出す（判定は変えない）。コンテナの開発イメージは Debian の ruff（2026-11-15 時点の testing は 0.16.10）なので、この WARNING は想定内。
- コンテナ: c3c 自身の開発用の `.c3c/packages.txt` に `ruff` を足す。
- 選ばなかった案: 設定を `ruff.toml` に置く（設定ファイルが 1 つ増える。規則の指定は 1 行で足りる）、CI で pip から入れる（Python の環境の用意が増え、shellcheck と取り方がそろわない）。
- 範囲外: B023 など F 系以外の規則、ops の PostToolUse hook（`lint-posttool.sh`）への ruff の追加。

**経緯:** `lint.sh` は Python（ルートと `tests/` の 34 本）の構文だけを確かめていて、静的な検査が無い（Issue #264）。ホストの ruff 0.16.4 で `--isolated --select F` を当てると 7 件出る（使っていない import 6 件、使っていない変数 1 件）。

作業ブランチは `feat-ruff-lint`（`main` の `6e2b37c` から）。計画の承認の直後に、計画者がブランチを作り、この計画を `docs/superpowers/plans/2026-11-15-ruff-lint.md` に写して commit する（公開の置き場。「計画レビューの記録」の一時パスと session ID は「（非公開の場所に保存）」に置き換え、commit の前に `grep -nE "$(id -un)|/tmp/|~/|session" docs/superpowers/plans/2026-11-15-ruff-lint.md` の出力を目で見て、ホストのパス・ユーザー名・session ID が残っていないことを確かめる）。実装者はその commit の上から始める。

**実行の場所:** すべてホストで行う（`./lint.sh` の Compose 検証に実 podman が要る。ホストの ruff 0.16.4 は利用者のホームの下にあり、`/usr/bin` には無い）。

## 全体の制約

**REQUIRED SUB-SKILL:** Use superpowers:test-driven-development（コードを変える計画。タスク 1 の前に 1 回読み込む）

- 固定値: `RUFF_VERSION: "0.16.4"`、`RUFF_SHA256: "9cb1234804ddb0f7f57cef3f81623ce5acb990e40af7cce08dc7778c9d7ee96c"`（`https://github.com/astral-sh/ruff/releases/download/0.16.4/ruff-x86_64-unknown-linux-gnu.tar.gz` のもの。同じ場所の `.sha256` と一致することを計画者が 2026-11-15 に確かめた）。tarball の中身は `ruff-x86_64-unknown-linux-gnu/ruff`。
- `LINT_REQUIRE_RUFF` は値がちょうど `1` のときだけ必須の意味にする（`0`・空・未設定は必須でない）。
- 文言（stderr。`printf` で出す）:
  - 無い・必須でない: `WARNING: ruff が見つからないため Python の静的な検査（ruff の F 系）をスキップしました（CI では LINT_REQUIRE_RUFF=1 で必須）。`
  - 無い・必須: `ERROR: ruff が見つかりません（LINT_REQUIRE_RUFF=1 では必須です）。`
  - 版違い: `WARNING: ruff の版（<手元>）が CI の固定版（<CI>）と異なります。版差で指摘が増減することがあります（#264）。`
  - 版は stdout に `ruff <版>`。版は `ruff --version` の出力の 1 行目の 2 語目（`read -r _ v _` で読み、後ろの付記は捨てる）。読めなければ（空）`ruff 不明` と出し、CI 版があれば版違いの WARNING の `<手元>` を `不明` にして出す。ruff が無いときは版の行を出さない。
- 判定の順: ruff の有無 → 版の表示と比較 → ファイルが 0 本なら ruff check を呼ばずに 0 → ruff check の終了コードが 0 以外なら 1。
- 挙動を変える commit には README の該当節を同じ commit に含める（root `AGENTS.md`「開発の進め方」）。
- 編集したら、そのターン内で `./lint.sh` を rc 0・警告ゼロで通す。日本語で書く。保守者個人のもの（ホストのパス、非公開のリポジトリの名前）をコード・試験・README に書かない。

## レビューで見てほしい点

1. ruff が入っているコンテナ（Debian の ruff が `/usr/bin` にある）で試験を回しても、「無い」場合の試験が本物の ruff を拾わないこと（タスク 2 の試験は `PATH` を試験用のディレクトリだけにする）。
2. `-` で始まる名前のファイルが ruff のオプションとして読まれないこと（`--` の後に渡す。タスク 2 の `clean_argv` が `-b.py` を渡して argv を完全一致で比べる）。`.` で始まる名前の `.py` も対象に入ること（タスク 2 手順 5）。
3. ruff 自体の失敗（終了コード 2、設定の誤りなど）を合格と扱わないこと（タスク 2 `ruff_internal_error`）。
4. `LINT_REQUIRE_RUFF=0` や空で必須にならないこと（タスク 2 `missing_require_zero`・`missing_require_empty`）。
5. CI で ruff の取得や版の確かめが失敗したとき、`lint.sh` まで進まずに赤になること（タスク 3 の手順。`set -euo pipefail` と `sha256sum --check`）。
