# GitHub Actions による CI の導入（設計）

日付: 2026-09-12。作成: Fable（計画担当）。実装: Codex（host）。レビューとマージ: Fable。

## 目的

lint.sh と test-build.sh のうち podman を必要としない部分を GitHub Actions で自動実行し、PR と main への push のたびに赤・緑が出る状態にする。
この repo には現在 CI が無い（進捗メモ「手入れ」項目）。

同時に、Fable が計画し Codex が実装から PR 作成までを担う工程の試運転を兼ねる。

## 範囲

含む:

- `.github/workflows/ci.yml` の新設。
- `lint.sh` への `LINT_SKIP_COMPOSE` 分岐の追加。
- README の検証に関する節へ、CI で何を回しているかの 1 段落の追記。
- 範囲外の項目を Issue として起票する（下記）。

含まない（Issue に残す）:

- `test-build.sh` 全体実行（実 podman build を含む）の CI 化。全体実行は FAIL があっても終了コードが 0 で終わるため、CI に載せる前に終了コードの修正が要る。#59（全体実行のたびに実台帳へ 1 行残る）も同じ前提の修正に含める。
- `podman compose config` の CI 実行（runner に compose provider が無い）。

## 調査で確定した事実

| 対象 | host での実測（2026-09-12） | ubuntu-24.04 runner |
|---|---|---|
| `lint.sh` | 2 秒、rc=0 | shellcheck 0.9.0 同梱（host は 0.11.0）。podman 4.9.3 はあるが compose provider が無い |
| `test-build.sh --validator-only` | 0 秒、PASS=82 FAIL=0、rc=0 | podman 不要 |
| `test-build.sh --launcher-only` | 2 秒、PASS=75 FAIL=0、rc=0 | podman 不要（ダミー podman。HOME を一時領域へ向けるので実環境を汚さない） |
| `test-build.sh`（引数なし） | 実 podman build、api.github.com、iptables が要る | 終了コードが常に 0 |

- `--validator-only` と `--launcher-only` は FAIL が 1 以上なら `exit 1` する（test-build.sh の各サブモード末尾）。
- `lint.sh` は `command -v podman` が真なら `podman compose -f compose.yml config` を実行し、失敗すると `status=1` にする。runner ではこれが赤の原因になる。
- shellcheck 0.11.0 の公式 tarball `shellcheck-v0.11.0.linux.x86_64.tar.xz` の SHA256 は `8c3be12b05d5c177a04c29e3c78ce89ac86f1595681cab149b65b97c4e227198`（host でダウンロードして計算し、展開したバイナリが 0.11.0 を報告することを確認）。
- `actions/checkout` の最新は v7.0.1、その commit SHA は `3d3c42e5aac5ba805825da76410c181273ba90b1`（gh api で解決）。

## 設計 1: workflow と lint.sh

### `.github/workflows/ci.yml`

- トリガー: `pull_request`（全ブランチ）と `push`（`main` のみ）。
- `concurrency`: 同じ ref の実行中ジョブは新しい push で取り消す。
- `permissions`: `contents: read` のみ。既定の `GITHUB_TOKEN` に書き込み権限を与えない。
- runner: `ubuntu-24.04` を明示する。`ubuntu-latest` は使わない。
- `timeout-minutes: 10`。
- 1 ジョブ、ステップは次の順:
  1. checkout。`actions/checkout` を上記 commit SHA で固定し、コメントに `# v7.0.1` を添える。
  2. shellcheck の取得。workflow の `env` に版と SHA256 を 1 箇所で書き、公式 Releases の tarball を取得して `sha256sum --check` で照合し、失敗したらそこで止める。展開したバイナリを PATH に載せる（`$GITHUB_PATH` へ追記）。
  3. `LINT_SKIP_COMPOSE=1 ./lint.sh`。
  4. `./test-build.sh --validator-only`。
  5. `./test-build.sh --launcher-only`。
- 各ステップは `run:` の終了コードがそのままステップの成否になる。`continue-on-error` は使わない。

### `lint.sh` の変更

- 環境変数 `LINT_SKIP_COMPOSE` が `1` のとき、`podman compose config` の検証を実行せず、stderr に「LINT_SKIP_COMPOSE=1 のため compose config 検証をスキップした」旨の WARNING を出す。
- 未設定または `1` 以外のときは従来どおり（podman があれば検証、無ければ既存の WARNING）。
- 先頭のコメントに、この変数の意味と CI で使っている旨を書く。

### README

- 「変更後の確認」節（README.md:398 付近）に、CI が `lint.sh`（compose 検証はスキップ）、`--validator-only`、`--launcher-only` を回していること、全体実行は CI の対象外であることを 1 段落で書く。同じ節の `lint.sh` の説明文に `LINT_SKIP_COMPOSE` の意味を 1 文足す。表記は日本語のみ。

## 設計 2: 検出力の確認と受け渡し

### 赤になることの確認（壊し方）

実装が緑になった後、使い捨てブランチから draft PR を出し、次の commit ごとに `gh pr checks` で赤を確認してから PR を閉じてブランチを削除する。本 PR の履歴には残さない。

1. 追跡済みスクリプトに shellcheck 違反を 1 行入れる。lint のステップで赤になること。
2. 1 を戻し、`test-build.sh` の `VBI_VECTORS` の期待値を 1 件だけ書き換える。`--validator-only` のステップで赤になること。
3. 2 を戻し、workflow の SHA256 を 1 文字変える。shellcheck 取得のステップで赤になること。

`--launcher-only` は `--validator-only` と同じ「FAIL が 1 以上なら exit 1」の経路なので、2 で代表させる。

### lint.sh の変更の確認（host）

- `LINT_SKIP_COMPOSE=1 ./lint.sh` が WARNING を出して rc=0 で終わる。
- 変数なしで、`podman` という名前の失敗するダミーを PATH の先頭に置いて `./lint.sh` を実行すると rc=1 になる（従来の挙動の回帰確認）。
- 変数なしで通常の host 環境なら rc=0（従来どおり）。

### 合格条件

- 本 PR の CI が緑。
- 壊し方 1〜3 がそれぞれ赤。
- host で lint.sh の 3 パターンが期待どおり。
- README の記述が実装と一致している（CI で回す 3 本、`LINT_SKIP_COMPOSE`）。

### Codex への受け渡し

- 設計（この文書）と計画を作業ブランチ `ci/github-actions` にコミットする。
- 計画には壊し方と合格条件を書き、Codex の `/goal` の停止条件としてそのまま使える形にする。
- commit メッセージ、PR の題名と本文は日本語のみ（repo の表記方針）。
- PR のマージは Codex が行わない。レビューとマージは Fable。

## 捨てた案と理由

- 全体実行を CI に載せる: 終了コードの修正と #59 が先に要り、試運転の範囲を超える。
- runner に `pip install podman-compose` を入れて compose 検証も通す: 版の管理が増える。今回は lint.sh の意図宣言で外す。
- workflow で PATH から podman を隠す: 何を検証していないかが workflow に埋まって読めなくなる。
- runner 同梱の shellcheck 0.9.0 をそのまま使う: host と判定がずれる。
- marketplace の shellcheck action: 外部依存とその版固定が増える。
