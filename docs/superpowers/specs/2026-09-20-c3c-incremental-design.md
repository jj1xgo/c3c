# c3c への増分移行 — 設計・段階計画

日付: 2026-09-20。調査基点: claude-container `93211ed`。

> 状態: Fable・Codex 標準レビューとセルフレビューの指摘を反映した案。ユーザーレビュー前。
> この文書は、提供する機能、変更の分け方、次へ進む条件を定める段階計画である。
> ファイル別の実装手順を確定した詳細実装計画ではなく、本書だけで製品実装・移行・改名を開始しない。
> 詳細実装計画は、各段階の前提を確認し、本書のユーザーレビュー後に別途作成する。

## 1. 目的と合意事項

現在の claude-container を引き継ぎ、Claude Code と Codex のどちらでも普段の作業を続けられる c3c に育てる。
c3c は Claude Code & Codex Container を意味する。初期対象は Linux と rootless Podman。当面は持ち主の利用環境で検証する。

- 同じリポジトリ、実装、修正履歴、Issue・PR、回帰テストを活用する。全面再実装・別リポジトリ新設は今回行わない。
- 現行 GPL と upstream の MIT 帰属表示を維持する。同梱ソフトウェアのライセンスも引き続き扱う。
- 最終的な起動名は `c3c`、設定ディレクトリは `.c3c/`。旧ディレクトリ名を恒久的な標準にしない。
- `c3c claude` / `c3c codex` で直接選択できる。`c3c` は初回選択、次回は同じリポジトリで前回使った CLI を既定にする。
- 素の CLI に近い操作感を優先する。対話 UI・モデル選択・MCP 管理等は各 CLI の標準機能を使う。
- 共通イメージに両 CLI を導入し、セッションごとに別コンテナを起動する。通常の checkout だけでも使える。
- 同時作業は同じリポジトリの別 worktree で行う。コンテナ内 AI が一覧・作成・選択し、同じ会話のまま作業を続けられることを目標とする。
- 長い worktree 名を利用者に覚えさせない。AI が作業内容と現状から候補を選ぶ。一意に決まらない場合は確認する。
- MCP・CLI 設定はリポジトリ単位で共通にする。worktree ごとの c3c 独自設定は作らない。
- handover と共有作業状態は設定可能な外部 Markdown 保存先を使う。利用者は既存 Obsidian vault を継続使用するが、製品は Obsidian に依存しない。
- CLI 固有の memory・履歴は保持する。相手 CLI への引き継ぎに必要な情報は作業別の共有 Markdown にも残す。
- 同じリポジトリの AI 同士は信頼する。worktree 間の使用中管理は事故防止であり、相互の悪意ある書き込みを遮断する境界ではない。
- 別 AI の自動起動・作業依頼・指揮・進捗集約は次のフェーズとする。

## 2. 今回の見直しと、変更しない目標

第1回レビューに従い、Codex 対応、名前の移行、設定形式・保存場所の再編を別々の変更単位にする。
TOML 化は `.c3c/` 改名の前提から外す提案であり、設定整理の範囲と順序は本書のユーザー確認を待つ。
ホスト側の許可領域の新設と、Claude の設定保存先の分離も独立した設計対象にする。
これらの順序変更を含む本書全体は、ユーザー確認後に確定する。

「コンテナ内で追加したユーザー設定はホストに自動反映せず、反映は明示操作にする」という目標は維持する。
ただし現状の Claude は `.claude.json` をホストと rw 共有しているため、この目標を達成済みとは扱わない。
共有 checkout の `.mcp.json` 等はホストからも読める別経路であり、ユーザー設定領域の分離だけで全経路を防げるとは主張しない。

## 4. 第0段階: 詳細実装計画を作る前の確認

以下を、関係する段階の詳細計画へ進むための判定点とする。文書上の指摘反映は、実測課題の解消を意味しない。
確認用の実行やプローブにも、対象、変更範囲、期待結果、元へ戻す方法を定める。既存の作業中 worktree を実験対象にしない。

### G1: リポジトリと worktree の単位（第2a・3段階の前提）

- 最終的な設定・イメージ・前回 CLI の記憶の単位は、同じ Git common directory を共有するリポジトリとする。別 clone は別単位とする。
- セッション ID と選択 worktree は別に管理する。同じブランチ名・同じ remote URL だけで同一視しない。
- 非 Git ディレクトリは従来のパス単位の起動を維持し、worktree 操作だけを適用しない。
- 現行の path 単位の台帳・イメージは直ちに付け替えない。既存エントリとの対応、移動・symlink・main/linked checkout からの起動を詳細設計で確認する。
- worktree ごとに異なる既存 MCP 承認は repo 単位へ合算しない。設定の実効内容と承認対象が同じことを確認できない場合は再確認する。
- repo 共通の c3c 設定を読む正本 checkout と、その選定・保存・不在時の診断を第3段階の詳細計画前に確定する。gitignore 対象の `env` と追跡対象のビルド入力が別 worktree では異なる点を扱い、起動先ごとの暗黙の切替を避ける。設定の読み込みは第2b段階までは現行の checkout 単位を維持し、新旧ディレクトリの診断対象も起動 checkout とする。
- CLI・MCP 設定の共通化も第3段階の独立した判定点とする。両 CLI ごとに、共通化するネイティブ設定源、標準の設定/MCP 登録操作の保存先、project/branch 側の上書きと実効値への影響を表にして確定する。設定ホームの共有だけで達成扱いにしない。同じ repo の別 worktree で共通化対象の実効設定が変わる場合は、そのまま進めず競合として診断する。標準 CLI のままで共通化と登録操作を両立できない場合は実測結果を持ち主へ戻し、「基底設定だけ共通」への変更を無断で行わない。

### G2: ホストとコンテナの Git パス（第3段階の前提、早期に確認）

相対参照の gitfile と、リポジトリ配下に置く worktree の組合せを第一候補として検証する。
Git は相対パスで worktree をリンクする標準機能を持つが、対応版・互換性を確認してから採用する。[Git 公式](https://git-scm.com/docs/git-worktree)

- ホスト・イメージ内の Git 版、worktree 側の `.git` と common directory 側の逆参照の両方を確認する。
- ホスト作成→コンテナ利用、コンテナ作成→ホスト利用の両方向で `status`、ブランチ識別、変更・コミット・再開が成立することを確認する。
- 新規の管理先はリポジトリ配下の共通領域として設計する。既存の `.claude/worktrees/` や兄弟ディレクトリの worktree は列挙・診断し、黙って移動・修復しない。
- Claude 標準の作成先と c3c の作成先が異なっても、同じ repo の Git 登録済み worktree を両方列挙する。列挙可能でも mount 外で利用できないものは診断し、選択可能とは表示しない。
- 第一候補で既存利用を維持できない場合は、必要な repo/worktree のみを同じ絶対パスで見せる案と比較する。ホーム全体の mount や Podman socket の公開は解決策にしない。
- `/workspace` と履歴の関連を保つ。パス方式の変更で履歴が見えなくなる場合は、その移行確認を方式選定の条件に含める。

### G3: Codex の権限・MCP・hook trust（第1段階の日常利用前提）

- コンテナを外側の強制境界とする現行のミッションを維持する。第0B-2/5/7段階の観測に基づき、通常作業は Codex の workspace-write、諮問は read-only を第一候補とする。必要な作業がこの方式で成立しない具体的な事例が出た場合に、コンテナ境界へ委ねる方式と比較する。権限を広げる比較自体を製品編集前の必須作業にはしない。
- 判断基準は、許可済みの作業・vault 利用・必要な通信ができること、未許可の通信と現行で保護対象とするホスト設定への書き込みを防ぐこと、故障時に無言で保護を解除しないこと。既存の `.claude.json` 共有の解消は G4 で扱い、第1段階で新たなホスト実行経路を増やさない。失敗を理由に自動的に広い権限へ切り替えない。
- 対話利用の既定モードと、諮問・レビューの read-only モードは分ける。比較結果と既定値を第1段階の詳細計画に固定する。
- MCP は user/project 設定、CLI 上書き、plugin 等、その版で有効になる設定源と優先順位を列挙する。`CODEX_DIR/config.toml` だけを見て網羅できたと扱わない。
- 任意コマンドを起動する stdio 定義等について、c3c の起動時に初回・変更後の人間の確認を行い、次回の確認省略に使う独立した承認記録を保護する。既存 TOFU と同様、その記録の保存先はプロジェクト入力から独立させ、コンテナ側から偽造・変更できないことを条件にする。Codex の project trust や hook trust を、そのまま c3c で人間が確認済みという証拠にはしない。
- CLI 標準の信頼確認で十分な範囲を先に調べ、不足する起動時の経路だけ既存ゲートの拡張対象にする。MCP の command/args/cwd/env 等と、HTTP型のローカルcommand経路も審査対象の判定に含める。設定解析不能・実効設定の判定不能を黙って許可へ落とさない。標準 managed 設定の部分一致を、定義全体の承認と同等とみなさない。
- 変更した定義、壊れた設定、未承認定義、前回セッションから書き換えた定義で確認する。定義の一致は参照コードの不変を保証しないという既存 TOFU の限界も残す。
- hook trust は標準 CLI 内の操作確認として明示的に再確認する。過去版の障害を現行版の事実とせず、対話起動・再開・非対話利用を区別する。native trust 状態全体の改竄防止を c3c が保証したとは主張せず、c3c 独立承認の代用にしない。
- 保証する時点は c3c によるコンテナ起動時の審査である。CLI 稼働中の設定追加・変更・再読込を常時監視する仕組みは、現行 Claude 側にも無く、今回の「既存機能維持」から追加しない。標準の登録・保存・再接続は維持し、稼働中の変更が実行に反映されうることを残余として説明する。後から継続強制を求める場合は、標準操作への影響を含む別の要件として判断する。
- 第1段階の計画確定条件は、既定権限、起動時に解決する設定源、審査定義、独立承認の保存・照合方式と不明時の拒否動作を具体化すること。通常起動/再開・refresh・vault・skill/memory・hook実行・Claude回帰は、製品実装後の受入として実施する。

### G4: 設定をホストへ自動反映しない目標（全体完了の前提）

Claude の `.claude.json` 共有は、改名では解決しない。認証・履歴を失わず、標準の MCP 登録操作を維持する分離案を独立して設計・実測する。
単に「project scope だけ使う」という規約では、共有 checkout を通じた反映も残り、当初の目標を満たしたことにしない。
第1段階は既存構成との比較試行として扱い、現状の共有と残余リスクを記録する。G4 未解消の状態を最終 c3c の受入完了とはしない。
必要な分離は第4段階で扱うが、第1段階の試行で新たなホスト実行経路を増やす場合は先行して対処する。

## 5. 第1段階: Codex の対話利用を成立させる

起動前の共通処理とガードは保ち、最後に選択した CLI を起動する。無指定の旧起動は Claude を維持し、新しい選択入口を追加する。
Codex 未導入・無効な選択・認証保存先の不備を診断し、別 CLI へ無言で切り替えない。
この段階では既存の opt-in 導入を維持し、評価用イメージに両 CLI を明示導入する。両 CLI の既定同梱への変更は第2b段階に割り当てる。

1. G3 のモード・MCP 確認方式を決める。初期プローブは使い捨て環境・限定した認証・確認済み設定で行う。
2. README「Codex CLI をセカンドオピニオンとして使う」にある `chatgpt.com` 等の既知情報を出発点に、対象版の認証/API/MCP 接続先を再確認する。まず利用側の既存 `allowed-domains.txt` と再ビルドで確認し、firewall を無効にして成功扱いにしない。
3. 通常起動、停止・再開、認証 refresh、MCP、hook trust、指示・skill・memory・履歴、vault の読み書きを確認する。
4. MCP の確認と外側の通信・権限制限を含む安全性の受入を満たしてから、実プロジェクトで日常利用を試す。
5. 「修正→検証→handover 保存→次のセッションで再開」を通し、介入・再認証・失敗を記録する。Claude の既存経路も確認する。
6. README のセキュリティモデルと `SECURITY-CLAIMS.md` に、Codex の審査対象・対象外・持続する設定の扱い・保証の限界を反映する。実測結果と記載が一致することを第1段階の受入条件にする。

日常利用の評価案は、持ち主が選ぶ2プロジェクトで各5セッション。安全性・データ喪失の問題は件数にかかわらず不合格とし、追加手間と未解決障害を説明して移行判断を受ける。
回数を消化したことだけで合格にしない。正式な評価対象は詳細計画で指定する。
主な変更候補は launcher・`entrypoint.sh` と対応テスト・README・`SECURITY-CLAIMS.md`。必要と実測で判明した部分だけ Compose/ビルド/ゲートへ広げる。

## 6. 第2段階: c3c という名前と `.c3c/` への移行

### 2a: 起動名とリポジトリ名

- GitHub の同じリポジトリを改名し、起動名 `c3c` と `c3c claude|codex` を提供する。
- 旧入口との互換を保つ間は、旧引数を黙って別の意味に解釈しない。GitHub 改名時は remote、README の URL、CI、利用側の起動経路を点検する。
- 無指定時の前回 CLI は G1 の単位で記憶する。CLI が利用不能なら診断して再選択できるようにする。非対話実行で入力待ちにならない契約を詳細計画に定める。
- 前回 CLI の記憶用 ID の導入で、既存の承認台帳やイメージ ID を一括移行しない。共通設定の参照元変更は第3段階とする。
- この変更で state directory、イメージの内部識別子、コンテナ内の `/workspace`・秘密の保存パスは変えない。MIT 帰属表示も維持する。

### 2b: プロジェクト設定ディレクトリ

- `.c3c/` を標準にする。中の `env`・行指向ファイルはこの段階では維持し、TOML へ同時変換しない。
- 両 CLI を既定で同梱する変更を、この段階の独立した変更単位として実施する。必要な Node/npm・Codex の版とビルド入力を詳細計画で固定し、新規設定と旧設定からの移行の双方で両 CLI の起動を確認する。既定イメージ内容の変更として SemVer とロールバックを別途判定する。
- 既存の `CLAUDE_CONTAINER_*` env キーは互換性のため維持し、ディレクトリと同時には改名しない。別名の追加が必要なら、優先順位・衝突診断を別変更として設計する。
- 移行期間は旧 `.claude-container.d/` も読めるようにする。両方ある場合は混ぜず、移行途中として診断・停止する案とする。
- `--check` で旧配置、二重配置、不正な型、参照切れを報告する。利用中のプロジェクトを列挙し、バックアップ・移行・旧版へ戻す方法を確認する。
- 移行は明示操作で行い、起動時に勝手にファイルを移動しない。移行後の build/run/check/clean と必要な追加検証を実物で確認する。
- 設定名の変更だけで MCP を再承認済みにしない。既存記録と実効定義・対象の同一性を確認できない場合は再確認する。
- 内部 state directory の改名は不要とする。移行を要する実際の理由が生じた場合に、旧記録の対応付けと二重読込を別途設計する。

後方互換を保つ追加と、既存利用を壊す変更を分けて SemVer を判定する。`.c3c/` 追加だけで機械的に MAJOR と決めない。
旧形式の削除を行う際は破壊的変更として別に判断し、事前診断を実機確認する。タグは承認後に付与する。

## 7. 第3段階: worktree 管理と共有記録

G1/G2 の結果をもとに、設定・イメージは repo 単位、選択作業先とプロセスはセッション単位に分ける。
worktree を選ぶたびに自動的に別イメージや設定ホームを作らない。CLI 本来の設定形式・優先順位を前提に、G1 で確定する共有契約を両 CLI で満たすことを受入条件にする。異なる `.mcp.json` 等を持つブランチへの切替と、標準操作による設定追加を検証し、共通化対象に意図しない差が生じる状態を合格にしない。

- AI が worktree とブランチ、変更有無、使用状況を読み、handover と照合して選択・作成する。古い記録だけで作業先を奪取・削除しない。
- 作業先の予約は、同時選択に対する原子的な取得・所有者の確認・終了時の解放・異常終了時の回復を定義する。ホストとコンテナで異なる PID だけを生存判定にしない。
- 標準のファイルロック等で十分か検証し、新たな常駐サービスを前提にしない。`git worktree lock` は削除・移動等の防止であり、同時編集の排他ロックの代わりにはしない。[Git 公式](https://git-scm.com/docs/git-worktree)
- 直接の Git 操作や c3c 外での起動を完全には検知できない。管理対象と検知できない利用を区別し、事故防止の保証範囲を明記する。
- 同じ repo の build/staging/イメージ更新も同時実行時の衝突を防ぐ。異常終了時の残留を含め、詳細計画でロック対象と解放条件を定める。
- 設定・認証の同時更新は各 CLI の挙動を実測する。設定は共通のまま、履歴等を無条件にコピー・合併せず、標準の保存方式を尊重する。
- 共有 Markdown はタスクごとに分ける。作業 ID、対象 repo/ブランチ/worktree、担当、更新時点、次の一手を記録する。ロックや権限の正本にはしない。
- 外部記録は現在の Git と稼働状態に照合する。古い handover、移動済み worktree、複数候補、同時更新を検証する。既存 vault の記録を一括改名・移動しない。

会話中の移動は、G2 を通した使い捨て環境で第1段階と並行して先行確認する。
CLI の作業基点、相対パスの読書き、shell、指示・hook、MCP の対象、履歴と再開先が一致することを両 CLI で確認する。
両 CLI で、会話内の移動による設定再読込と MCP の起動タイミングを実測し、移動先の未承認・変更済み・解析不能な実行定義を実行前に止められることを第3段階の前提にする。起動時の launcher/entrypoint 審査だけでは満たしたことにしない。承認済み A から未承認 B への移動、B の設定変更後の再移動、判定失敗を受入ケースに含める。必要な審査が標準機能等で成立しなければ、その移動を許可せず方式を再検討する。検証用の移動も使い捨て環境・無害な確認用定義に限定する。
子プロセス内の `cd` や `codex -C` の起動成功だけで、既存会話の基点切替成功と判断しない。
標準機能で成立しない場合は結果を持ち主へ戻し、独自機構の追加やセッション再起動への要件変更を無断で行わない。

## 8. 第4段階: 設定保存と許可の整理を個別に判断する

G4 のユーザー設定分離とホストへの明示的取り込みは、全体要件として残す。MCP 登録、再認証、履歴・memory、ホストへの反映、戻し方を実測して設計する。
ホスト側の mount/通信許可領域の新設は、現在の「利用側設定を運用者が管理する」モデルからの変更である。
利用中の設定・必要な操作回数を調べ、移行負担と安全上の効果を説明する。改名だけの変更に紛れ込ませない。
TOML 化は、現形式の何を解決するか、parser 依存、ビルド入力検証・staging・Dockerfile・診断への影響を比較して採否を決める。
いずれもユーザー判断を経る。延期中は「すべての設定分離が完成した」と説明しない。

## 9. 検証と引き渡し

- 変更した境界とガードは、[README の変更後の確認](../../../README.md#変更後の確認)に従う。`./lint.sh`、対象の launcher/validator/回帰テスト、必要な実 build と runtime 検証を行う。
- コンテナ内で Compose 検証を省略した場合は not run とし、Podman を使えるホストまたは CI で補完する。必ず持ち主が手作業で行うという前提にはせず、実行可能な担当環境へ割り当てる。
- PR 必須の `ci.yml` は Compose 設定検証とビルド不要のテスト等を扱う。別の `runtime.yml` は手動・定期実行で実 build・mount 保護・権限・IPv4 通信を検証するため、該当範囲の補完に利用できる。対話 CLI・認証・IPv6 等の対象外項目は、実行可能な Podman ホストへ別途割り当てる。workflow の存在と対象版での検証成功を区別する。
- entrypoint の共通初期化と抽出境界コメントを保ち、CLI 選択の変更が IPv6/refresh/秘密の配線を壊さないことを対応テストで確認する。
- IPv4/IPv6 の許可・拒否通信、capability、ホスト設定保護、認証 refresh、停止/再開は実コンテナで確認する。静的レビューだけで動作保証しない。
- 各段階の詳細計画に、対象ファイル・具体的な検証コマンドと期待結果・失敗時の扱い・ロールバックを書き、レビューしてから実装へ渡す。
- 計画の確定前に writing-plans のセルフレビューと独立レビューを行う。Codex 標準レビューへ計画全文・要件・審査観点を渡し、計画審査に不十分なら読み取り専用の独立レビュアーを使う。Fable を含む各レビューの Critical・Important は根拠確認、修正、確認限定巡を経て未対応を0件にする。標準出力の P2 等を Minor と機械的に対応付けない。却下には根拠を残し、未実測の前提条件を解消済みとは扱わない。上限巡で残件があれば計画を確定せず、残件と次の判断を報告する。
- 前段階が成功しても全体の受入完了とはしない。G4 などの残要件を明記し、段階的な利用移行と最終完了を分ける。

## 12. G3レビューの解釈訂正（第0B-9段階）

前回の独立レビューで、起動後の全変更に対する継続強制と、native hook trust全体の偽造防止を必須と読んだ指摘があった。現行 launcher・entrypoint・README の残余記載に照合した再診断で、その読みは既存TOFUより広いとレビュアー自身が訂正した。本書G3は、c3cの起動時審査と確認省略に使う独立承認記録を保証対象として明確化する。外側の通信/権限境界、保護対象のホスト設定、独立承認記録の保護は維持する。

これは全native状態の改竄防止や稼働中の全実行許可を達成したという主張ではない。根拠: [現行READMEのセキュリティモデル](../../../README.md#セキュリティモデル)、[entrypoint](../../../entrypoint.sh)、[マウント不変条件](../../development-invariants.md)。詳細実装計画では、起動時の設定解決が実行を伴わない範囲と未対応時の拒否を別途検証する。
