# `-b` でベースイメージと Debian パッケージのセキュリティ更新を入れる 設計

**状態:** 設計の合意済み（持ち主 2026-11-06）。builder check を反映済み。持ち主の spec レビュー待ち。
**区分:** 境界（ビルドの手順と、`Dockerfile.claude` のビルド時アサーション〈`docs/development-invariants.md`〉に触れる。利用者全員の既定の挙動が変わる）。
**関連:** [#248](https://github.com/jj1xgo/c3c/issues/248)（事実の記録と、当面の手当てを試した結果のコメント）。

## 目的

c3c の利用者が、特別な手順を踏まなくても、Debian のセキュリティ修正（OpenSSL など）を受け取れるようにする。

今は `c3c -b` で再ビルドしても、更新が入らない（#248）。

1. ベースイメージを取り直さない。`run_explicit_build()`（`c3c`）の `podman compose ... build` に `--pull` が無いので、ホストに一度 pull したベースを使い続ける。
2. apt の層がビルドキャッシュに残る。`CACHEBUST` が効くのは Claude Code を導入する層だけで、`ca-certificates`・固定のパッケージ・gh・`packages.txt` の apt の層は、Dockerfile の行と入力が変わらなければキャッシュを使う。`apt-get upgrade` も無いので、ベースに最初から入っているパッケージは、ベースの時点の版のまま残る。

2026-11-06 の実測では、既定の `debian:stable`（2026-08-24 作成）に `stable-security` の更新が 6 件（libssl3t64 など）未適用だった。今日ビルドしたイメージでも、29〜42 件が古いままだった。ベースを手で pull すると、`FROM` から後ろのキャッシュが全部外れた。その結果、残りは 2〜3 件（ベースの作成の後に出た分）まで減った（#248 のコメント）。

## 成功条件

- `c3c -b` の直後のイメージで、root で `apt-get update && apt list --upgradable` を走らせると、0 件になる。例外は、ビルドの最中に archive が更新された場合と、パッケージを消さないと上がらないもの（`apt-get upgrade --with-new-pkgs` の kept back。下の「実装に任せること」）だけ。
- これはベースの指定（既定の `debian:stable`、`debian:testing` などの動くタグ、日付タグ、digest pin）によらず成り立つ。
- ホストのベースより新しいベースがレジストリにあれば、`c3c -b` がそれを使う。
- イメージが無いときの初回のビルドも、どの経路（Claude、Codex、project 設定ゲートの有無）でも、`-b` と同じ取り直し・upgrade・失敗時の停止になる。compose の暗黙のビルド（`run --build` 相当）には頼らない。
- ベースの取り直しが失敗したら、`c3c -b` は理由を表示して、0 以外で止まる。古いイメージは消さずに残し、起動へは進まない。
- 作成から一定の日数（既定の目安は 30 日）を過ぎたイメージで起動すると、WARNING が出て、`-b` での再ビルドを案内する。起動は止めない。`--check` でも同じことを報告する。
- 境界のビルド時アサーション（`setpriv`・`tini` の存在、`setpriv --ambient-caps`/`--inh-caps` の受理、apt sources に `http://` が残っていないこと）は、upgrade の後のイメージに対しても成り立つことを、ビルドの中で確かめる。

## 持ち主が決めたこと（2026-11-06）

1. `-b` のたびに最新にする。ベースは新しければ取り直し、apt の更新も当てる。ビルドが数十秒ふえるのは受け入れる。
2. ベースの取り直し（レジストリへの問い合わせ）だけが失敗したときも、ビルドを止める（fail-closed）。手元のベースで続けることはしない。
3. 固定の有無によらず、`-b` では upgrade を掛ける。`-b` は「作り直して」という明示の指示だからである。固定（日付タグ、digest pin）で守れるのはベースの版だけで、apt のソースは `deb.debian.org`（その日の最新）を指している。そのため、`apt-get install` で入るパッケージは、もともと `-b` の時点の最新になっている。
4. `-b` を長く打たない利用者のために、起動のときに「イメージが古い」と WARNING で知らせる仕組みも、この作業で作る。固定の有無によらず出す。
5. イメージが無いときの初回のビルドも、`-b` と同じにする（取り直し、upgrade、失敗したら止める）。今は経路によって扱いが違う。`run_explicit_build()` を通るのは、`-b`、イメージが無い Codex の経路、イメージが無い Claude の project 設定ゲートの経路だけである（`c3c` の `if [[ $BUILD -eq 1 || ...` の行）。ゲートの無い Claude の経路は、`run_main_compose()` の `compose run` の暗黙のビルドになる。そこには pull が無く、`CACHEBUST` は既定の `unknown` のままで、ビルドが失敗すると古いイメージで起動する（fail-open）。しかも作成日が今日なので、古さの WARNING も出ない。この経路も明示のビルドに通す。初回の起動にもレジストリが要るようになり、失敗したら起動を止める。
6. ベースが新しくなった直後の `-b` は、キャッシュが全部外れて丸ごとのビルドになる。それでも、`-b` のたびに取り直す（頻度を抑える仕組みは作らない）。

## 非目標

- 動いているコンテナの中で更新すること。ランタイムの firewall（`deb.debian.org` を許可しない）は変えない。
- 古いイメージや、宙に浮いたイメージ（`<none>`）を自動で消すこと。
- apt を `snapshot.debian.org` に固定するなどの、ビルドの完全な再現性。
- `.c3c/` の新しい設定（upgrade を切る設定、日数の設定など）。設定の形は増やさない。
- `test-build.sh` の `podman build --no-cache` の経路を変えること（`--no-cache` で apt の層は毎回作られる）。ただし、追加した層とアサーションがそこでも通ることは確かめる。

## アンチゴール（技術的に動いても失敗とみなすもの）

- upgrade の層を前のほうに置き、毎回その後ろの層がすべて作り直されるようにした（ビルドが毎回分単位で遅くなる）。
- ビルド時アサーションを、upgrade より前でしか走らせていない（upgrade で `setpriv` や apt sources が変わっても気づかない）。
- 取り直しの失敗を握りつぶし、古いベースで黙ってビルドを続けた。
- 古さの WARNING が、作ったばかりのイメージにも出る。あるいは、WARNING を出すためにネットワークへ問い合わせる（起動を遅くし、オフラインで壊れる）。
- `.c3c/base-image.txt` の検証（`guard_base_image()`）や、ベースの既定値の 3 か所の重複（`docs/development-invariants.md`）を崩した。

## 実装に任せること（builder の判断）

ここに挙げたものは、私（計画者の Opus）の判断である。持ち主の決定ではないので、根拠があれば変えてよい。変えたら、計画にその理由を書く。

- **取り直しの方法:** compose の build の前に、`podman pull "$BASE_IMAGE"` を別に打つ。その終了コードが 0 以外なら、レジストリの失敗として理由を出して止める。`--pull=newer` は使わない。`man podman-build` に「Pull errors are suppressed if a local image was found.」とあり、手元にベースがあると失敗が握りつぶされるからである（builder check の指摘を確かめた）。digest pin でも問い合わせは要る。`apt-get update` もネットワークを要するので、決定 2 の範囲と見る。apt の失敗は、compose の段の失敗として分けて表示する。
- **upgrade の層:** 毎回作り直される層の近く（今の `CACHEBUST` の層は `USER node` の後にあるので、root で走る別の層が要る）に、`apt-get update && apt-get upgrade -y --with-new-pkgs` の層を置く。`full-upgrade` は使わない。パッケージを消すことがあり、固定の層の `iptables`・`sudo` などや `packages.txt` のものが消えても、今のアサーションでは気づけないからである。消さないと上がらないもの（kept back）は残る。成功条件の「0 件」は、kept back を例外とする。キャッシュを外す値は、`CACHEBUST` と同じものを渡すか、新しい `ARG` にするかを決める。gh の公式リポジトリも apt のソースに入っているので、gh もここで上がる。
- **アサーションの再実行:** 今のアサーションの層を upgrade の後へ移すか、upgrade の後に同じ検査をもう一度走らせる。検査の中身を 2 か所に書くのを避けるなら、スクリプトに出す（そのときは不変条件の文書と README の該当節を直す）。
- **古さの判定:** イメージの作成日（`podman image inspect` の `Created`、またはビルドの時点で付ける label）と今日の日付で判定する。ネットワークは使わない。目安は 30 日。既存のドリフト診断（起動時の `WARNING` と `--check`、`c3c` の `ASSET_HASH_TARGETS` の周り）の出し方と揃える。
- **README:** 「変更後の確認」「イメージの変更」「利用側プロジェクトの設定」の `base-image.txt` の項を直す。再現性の案内（「再現性が必要なら日付タグか digest pin」）は、固定で守れるのがベースの版だけで、apt のパッケージは `-b` の時点の最新になる、と分かるように書き直す。`-b` がネットワーク（レジストリと `deb.debian.org`）を要すること、失敗したら止まることも書く。
- **テスト:** `test-build.sh` の compose の呼び出しの記録（`compose-args.<n>`）で、`-b` の build に取り直しの指定が付くことを確かめる。古さの WARNING は、作成日を差し替えられる形で、境界の前後（29 日、30 日、31 日など）を確かめる。実ビルドで upgrade の後の件数が 0 件になることは、ホストで確かめる（CI は実 podman build をしない）。
- **SemVer:** 既定の挙動が変わるので minor を見込む。タグは、実装と PR 後のレビューの後に提案する（root `AGENTS.md`）。

## 確かめ方

- `./lint.sh` が終了コード 0、警告ゼロ。
- `test-build.sh` の該当するモード（README「変更後の確認」節の一覧に従う）。
- ホストで、既定の `debian:stable` のプロジェクトと、`debian:testing` のプロジェクトを、それぞれ `c3c -b` で作り直す。その後、`apt list --upgradable` が 0 件であることを確かめる。
- レジストリに出られない状態（例: レジストリの名前を引けなくする）で `c3c -b` が止まり、古いイメージが残ることを確かめる。
- 作成日が古いイメージで起動したとき、WARNING が出ることを確かめる。
